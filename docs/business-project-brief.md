# Material Agent 业务问题与技术方案

本项目面向物料主数据治理与采购申请审核，将物料定位、库存与订单核对、采购测算、人工审批和执行核验组织为可追溯的业务流程。下文先给出可直接使用的项目介绍与亮点，再说明业务痛点、项目目标及各环节的实现方式。

## 一 项目介绍与亮点

### Agent 驱动物料治理与采购决策辅助系统

物料录入与采购申请需要跨物料台账、库存和历史订单核对，同物异名、规格混淆及在途数量不清容易引发重复建码、重复采购和库存积压；人工拼接证据耗时，直接由模型写入业务系统又缺少授权与执行确认。项目目标是让 Agent 完成可追溯的物料归因、重复风险识别和采购影响测算，将业务动作转化为有证据、有审批、可恢复、可核验的提案。

- **对齐多源物料证据：** 面向同物异名与跨系统口径不一致，通过 MCP/CLI 统一读取并校验物料、库存和采购记录；歧义时请求补充信息，让采购判断有据可查。
- **约束推理与上下文：** 将物料核查与提案组织为显式阶段，按阶段限定 pi 工具；分层保留任务、证据和策略，压缩历史轨迹，减少过时信息对判断的干扰。
- **识别重复采购风险：** 针对库存和订单状态混用，按有效库存与已确认在途核算供应，结合需求测算采购缺口、建议量和金额，为人工复核提供依据。
- **守住执行与审批边界：** 在 PreToolUse 校验身份、阶段与风险，将高风险动作转为提案，并绑定版本、参数和幂等键审批，防止越权写入与旧批准复用。
- **闭合恢复与结果验证：** 针对审批等待与执行中断，以 SQLite 保存进度并查询 ERP 幂等结果，恢复时核对授权、执行后核验落地内容，避免重复建单。

## 二 业务痛点与项目目标

### 物料定位依赖经验容易选错或重复建码

采购人员可能只拿到“轴承”等名称，同一名称下存在多个规格，历史记录还可能使用别名。仅按名称命中一条记录，无法确认它是否就是需求中的物料；没有找到某个关键词，也不能据此断定物料不存在。

项目目标是先确认物料身份，再进入采购或录入流程。检索优先匹配编码，名称和别名结合规格、单位判断；候选不能唯一确定时请求补充信息。拟新增物料还需按自身编码、名称和别名再次查重，已有物料返回复用建议，证据不足时暂停。

### 库存和订单状态不清容易误判采购需求

账面数量不等于可供使用的数量：冻结与报废库存不可用于本次需求，已确认订单可能只收到一部分，而历史完成订单不能再次算作在途。人工只看库存总数或采购总量，容易把供应算多或算少。

项目目标是明确“能用多少、还会到多少、还缺多少”。按状态和剩余数量核算可用供应，将需求、安全库存和本次申请纳入同一测算，给出建议采购量及超额申请金额。存在库存或在途表示需要复核，新增采购是否合理仍结合需求判断。

### 判断和执行缺少证据与责任边界

一句“建议采购”不足以说明判断依据，也无法回答使用了哪笔库存、哪类订单以及哪些约束。模型若能直接改变数量或写入业务系统，错误归因可能进一步变成错误采购单。

项目目标是让模型负责受约束的工具调用与证据解释，让代码规则负责身份一致性、数量金额和执行授权。提案保留参数和证据，审批者确认具体版本；业务用户只能处理自己的会话，身份和角色从服务端 token 配置取得。

### 审批等待与执行中断容易导致重复操作

采购审核可能跨越多次运行，审批后需求也可能修改。尤其在“订单已写入，但应用还没记录结果”时重新执行，容易生成第二笔订单；把旧批准用于修改后的提案，也会改变审批者原本确认的事项。

项目目标是保存任务进度和审批绑定，需求变化后重新取证并使旧审批失效。恢复先确认外部动作是否已完成，成功后再核验结果，避免仅凭本地状态决定重写。

## 三 从业务需求到结果验证的完整链路

整体链路为：业务需求 → 数据接入 → Agent 推理 → 上下文控制 → 动作提案 → 权限拦截 → 人工审批 → 恢复与受控执行 → 结果验证。

上下文控制贯穿推理过程，权限检查发生在每次工具调用之前；链路中的动作先形成可审阅提案，实际写入在权限与审批通过后发生。

### 业务需求转化为有约束的任务

用户通过 API 或 CLI 提交采购任务或物料录入任务。采购任务包含物料线索、规格与单位约束，以及需求量、安全库存和申请量；物料录入提供拟新增主数据。系统把任务、所属用户和当前阶段保存为 Session。

字段缺失和负数、错误单位等不能被模型猜测补齐。无法确定物料或缺少测算要素时，系统返回 NEED_MORE_EVIDENCE，业务人员补充后从物料发现阶段重新推进。

### 数据接入先统一合约再校验事实

物料、采购历史和库存通过统一 DataSource 读取，支持本地数据、实际运行的 MCP stdio 客户端与服务端，以及 CLI JSON 子进程适配。MCP 支持工具发现与参数校验；CLI 只执行配置登记的程序和参数，通过标准输入输出传递 JSON。

进入证据层前同时检查结构与业务身份：候选重新匹配查询约束，详情必须与已选候选一致，库存和采购记录必须属于目标物料。工具失败、超时或脏数据按错误返回，不伪装为成功查询或零库存。结果持久化为带来源和标识的 EvidenceRef，供后续判断与审阅。

### Agent 推理在阶段和事实范围内进行

业务状态机决定当前需要完成的步骤；pi Agent Runtime 负责模型交互及工具调用。在允许阶段中，模型可选择额外只读工具，并通过 record_attribution 提交基于证据的解释和未校准置信值。选定物料、任务数量和策略约束由服务端绑定，模型输出不能替代这些约束。

采购流程依次完成物料发现、归因、重复校验、影响测算和提案。歧义交由业务人员澄清；模型调用设置轮次和时间预算，未产生有效工具结果时进入相应错误或恢复状态。默认演示使用明确标记的固定模拟模型流，真实模型解释质量仍需独立验证。

### 上下文控制保留判断所需的信息

长流程中的历史对话和重复工具结果容易占满上下文，也可能让当前任务被过时信息干扰。项目将 ContextPack 按任务、证据引用、工具轨迹、状态和策略分层，按当前阶段提供结构化输入。

上下文为证据引用、事实摘要和历史轨迹设置预算，优先保留近期信息，较早轨迹压缩为摘要。原始工具结果完整保存在 SQLite，截断摘要明确标记，任务与策略不由普通历史摘要覆盖。外部返回文本作为数据处理，不能替代工具权限或业务规则。

### 执行动作先成为有依据的提案

重复校验给出已有物料、有效库存、未完成采购及历史订单的证据。采购测算采用公式：**建议采购量 = max(0，需求量 + 安全库存 − 可用库存 − 已确认在途量)**。同时计算申请后的预计库存、缺口、超额申请量和金额；金额以最小货币单位存储并检查溢出。

Proposal 固化拟录入物料或申请采购量、证据引用、版本、参数摘要和幂等键，供审批审阅。采购提案使用用户申请量，建议量作为决策依据；若希望改为建议量，需要业务用户修改任务并形成新版本。物料录入查到已有物料时结束为复用建议，未命中且新增字段完整时才提出录入动作。

### 权限拦截检查每一次工具调用

所有工具经统一 Router 执行，PreToolUse 策略根据登记的风险、允许阶段、身份、证据完整性和审批绑定作出 ALLOW、APPROVAL 或 DENY 决策。L0 查询和 L1 校验测算在身份与阶段通过后可执行；L2 提案要求证据与规则通过；L3 模拟 ERP 写入要求批准当前版本。

工具风险由服务端注册表确定，请求体中的角色或模型声称的低风险不能改变它。调用还需匹配会话、已选物料和提案参数，防止把合法工具用于其他物料或其他用户的任务。API 与 CLI 共用应用服务及权限规则。

### 人工审批确认的是具体业务动作

审批角色查看提案及相关证据，提交批准或拒绝与原因。批准记录绑定 sessionId、工具、proposalId、版本、argsHash 和 idempotencyKey；修改需求后，旧批准失效，新的执行必须匹配新提案。

审批决定仅更新审批记录，由业务用户调用 resume 继续推进。拒绝后保留提案与原因，同版本不会自动重新执行。这样能区分“生成建议”“确认动作”和“执行动作”，并保存每一步的责任与依据。

### 恢复先核对已发生的动作

状态迁移与 checkpoint、状态事件在事务中保存，审批创建和等待审批状态同事务绑定。执行租约防止同一会话并发推进，乐观版本检查防止旧状态覆盖新状态。相同幂等键与参数复用结果，不同参数复用键返回冲突。

模拟 ERP 将业务写入和幂等结果一起提交。若写入后应用中断，恢复先查询 ERP 幂等记录，再验证审批与参数；已提交的匹配结果可以在模型不可用时直接核验，无需重新写入。只读工具限次重试，写入结果无法确认时进入 RECOVERABLE，按幂等合约恢复。

### 验证实际结果后才结束流程

工具返回成功不足以代表业务正确落地。Verify 检查实际执行记录的动作类型、参数摘要及 payload 是否与批准提案一致；物料录入还核对落地的主数据。通过后才标记 COMPLETED，差异保留为错误供排查。

模型调用、工具结果、策略决定、审批与状态变化记录为审计事件，为业务复查和评测提供依据。固定场景与故障注入进一步检查是否存在未批准写入、重复写入、审批改版失效或恢复失败。

## 四 一个采购场景如何体现业务价值

业务人员申请采购某规格轴承。系统查到可用库存和未完成采购，同时存在冻结、报废库存及已完成历史订单，需要先厘清哪些记录能够用于本次需求。

系统按物料身份和业务状态关联证据，扣除预留库存与已收货部分，排除不可用库存和已完成订单，再结合需求与安全库存测算缺口。若申请量超过建议量，提案呈现差异及依据，供审批者判断是否继续采购。

审批者可以基于业务原因批准原申请；若业务人员决定调整数量，应修改任务、重新生成提案并审批。批准后模拟 ERP 按提案执行并核验，等待审批期间不写入，重复恢复复用已有结果，避免重复建单。

## 五 技术选择与实现落点

**Node.js 与 TypeScript：** 严格类型与统一领域接口贯穿 Task、ToolCall、ToolResult、EvidenceRef、Proposal 和 PolicyDecision，减少 API、CLI 与工具适配之间的合约偏差。Fastify 提供 HTTP 入口和 OpenAPI，CLI 复用 Application；首版不增加 Web 前端。

**pi Runtime 与显式状态机：** Planner 负责模型交互和阶段内工具调用，Workflow 负责流程推进、等待、补证据与恢复。两者组合使自然语言解释受到业务阶段约束，Domain 负责可复查的物料匹配、状态过滤和数量金额计算。

**MCP 与 CLI 适配层：** 本地 stdio 服务提供只读数据工具；统一 DataSource、Zod 参数及结果 schema 将接入差异收敛为一致合约。固定子进程配置、超时与输出限制约束调用范围，模型无法生成任意 shell 命令。新的真实数据源需要遵循合约完成映射和校验。

**SQLite 与统一执行控制：** Session/Store 保存证据、提案版本、审批、checkpoint、执行和事件，Harness/Router 统一检查权限与风险，Verify 核对实际结果。SQLite 中的模拟 ERP 使执行与幂等恢复可重复验证；接入真实 ERP 后仍需对方提供结果查询与幂等合约。

**测试与评测：** Vitest 覆盖领域规则、会话隔离、MCP/CLI 子进程、pi 流适配、审批与故障恢复。Benchmark 使用独立标注检查检索、归因、重复识别、工具选择、权限违规、恢复和端到端结果，CI 在 Windows 与 Linux 的 Node.js 24 环境运行相同工程验证。

主要实现位置为 src/agent、src/domain、src/tools、src/context、src/harness、src/session、src/verify 与 src/benchmark；配置由 src/config.ts 管理，接口入口位于 src/api 和 src/cli.ts。运行步骤、完整接口和配置字段见 docs/project-overview.md。

## 六 当前验证结果与业务接入边界

现有测试与离线评测覆盖采购、物料录入、歧义补充、数据缺失、审批批准与拒绝、重启及写后中断恢复，并检查越权调用和重复执行。工程交付已完成类型检查、构建及 Windows/Linux CI 验证。

离线评测使用固定合成场景，被拦截或失败的调用保留在审计记录中。恢复故障采用受控注入，不代表生产断电或分布式压力验证。

当前物料、采购及库存均为合成数据，执行对象为可持久化的模拟 ERP。真实模型配置及 MCP/CLI 适配能力已实现；真实模型因缺少凭据尚未验证，真实 ERP 与企业数据尚未接入。离线指标说明固定案例中的工程行为符合预期，不能推出真实业务准确率、审批效率提升比例或采购节约金额。

后续业务落地应先验证真实模型，再接入真实只读数据，建立由业务人员标注的评测集并开展小范围审核试用。开放生产写入前，需要补齐企业身份、审批有效期与组织职责分离、数据时效检查、真实 ERP 幂等查询，以及部署监控和恢复策略。
